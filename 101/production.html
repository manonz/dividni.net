Getting multiple script versions: Producing a Dividni MCQ test or exam

Producing an exam means generating the requisite number of versions of exam scripts and associated OMR sheets. There are three "use cases" here:

  1. Proofreading your questions in an actual versioned exam setting. For this purpose, you will usually want to produce a small number of versions, say 10. Course staff can then proofread these 10 versions. Proofreading is best done with proofreading markup - these are markers (***) that Dividni puts into the script in front of either the correct answer option for truth questions, or in front of the correct statements (if any) for XYZ questions (note you will not see any markup for XYZ question versions where Dividni has picked three incorrect statements for the version). Proofreading is especially useful to reveal:
    • Statements / answer options that, in combination, contradict each other or give away the veracity of another option or statement,
    • Formatting issues (e.g., too little working space or risk of margin or page overruns), or
    • Numerical mistakes (for parameterised questions).
  2. Production for printing that requires each version to be in a separate PDF file. This is most commonly what external printing contractors require.
  3. Production for Assessment Services Exam printing. This requires all versions to be concatenated into a single large PDF file.

Production for proofreading

This requires that you tick either the "Proof copy (not for examination)" at the bottom of the "Edit Assessment Setup" / "Exam Setup" dialog or that you choose the option at production time from the "Generate Final Exam Scripts" menu.

To produce your proofreading run, click on "Generate Final Exam Scripts" at the top right of the exam preview window.

Under Paper Count, enter 10 (or whatever number of versions you want to generate for proofreading).

As the StartID, you can choose anything. Best practice is to use a StartID that ensures that the range of version numbers you will create is different from those generated for the actual exam - in case someone / something leaks the proofreading scripts to students, this prevents a situation where the answers to some scripts are known and those of others aren't. For example, if you set StartID to 20, this will generate versions 20 to 29 (for 10 versions). You could then use the default of 42 for the StartID for your actual exam script versions.

Unless you plan to do all of the proofreading yourself, you probably don't want to tick the "Single (large) PDF" box.

Hit the "Generate final exam scripts" button.

When done, Dividni will prompt you to download the "ground truth" answer files as a ZIP file. You must download them, but for the act of proofreading, you do not actually need them. Once you have downloaded the "ground truth" answer files, Dividni makes a link to the actual scripts available.

Do not forget to proofread the prologue (front page and instructions) - most Assessment Services rejects relate to issues on this page!

Production for printing

If you've previously been proofreading, ensure that the "Proof copy (not for examination)" at the bottom of the "Edit Assessment Setup" / "Exam Setup" dialog is turned off and the setup saved as such.

Click on "Generate Final Exam Scripts" at the top right of the exam preview window. 

Under Paper Count, enter whatever number of versions you need. Generally, you will want that to be class size + X. In other words: One individual version per student enrolled and then some extras in case people spoil their scripts or you drop them in the rain or you do need to split the test or exam across multiple theatres after all. Assessment Services generally want 20% more script versions for the exams than there are students.

As the StartID, choose a number that doesn't overlap with any range that you have used for proofreading. I usually like to generate two basic tests or exams - one for the class that sits it on the day and another (with a few questions swapped out) for any stragglers who sit later as a result of aegrotats etc. In this case, ensure that the StartIDs of both are sufficiently different so there are no overlaps - this allows you to tell scripts apart if students come and see you later. 

The default of 42 for the StartID is a nod to Douglas Adams and his answer to the ultimate question of life, the universe and everything.

Tick the "Single (large) PDF" box if you are producing scripts for submission to Assessment Services.

Hit the "Generate final exam scripts" button.

This can now take some time, depending on how many questions you have in your exam and how many versions you need to produce. An exam with 40 questions and 1000 versions can take in the order of a couple of hours to produce. Do not close your browser - there will be a progress bar. Needless to say it is not a good idea to start this process when you are about to pack up your laptop to go home!

When done, Dividni will prompt you to download the "ground truth" answer files as a ZIP file. You must download them and store them in a safe place as you will need them for marking (if you lose them or your computer dies or whatever, we may not be able to help you). Download and store them every time you have made changes to the test / exam as they may have changed also.

Once you have downloaded the "ground truth" answer files, Dividni makes a link to the actual scripts available.

Instructions to printing contractors

Printing a Dividni test or exam is a bit of an unusual task for a printing contractor: Normally, they print N copies of 1 document. We need to ask them to print 1 copy of N documents, staple them and - recommended for large classes to ensure embargo until official start time - inserted into an A4 envelope each.

Here are the instructions we use (adapt for your own assessment):

Could we please have all of the [number of scripts] PDF files in the attached ZIP file printed individually for the DIVIDNI 101 test. The ZIP format opens with Winzip or 7zip.

We need:

- double-sided printing
- each printout stapled in the top left corner
- each printout inserted in a plain A4 envelope and sealed
- everything here by [date a couple of days before the test] ideally (the test is
on [actual test date and time])

The last bullet ensures that there is time for contingencies (mis-printing, lost deliveries etc.)

What could possibly go wrong?

Actually, a lot!

  • If you see an error message during the production of an exam that didn't appear during the the preview, the most likely cause is a mismatched HTML tag in an answer option or statement that does not always appear in each version. This most commonly happens in questions where you have applied some formatting (e.g., bold, italics, fixed-width font, super- or subscripts): 
    • E.g., a matched HTML tag for a superscript looks like this: 500 m<sup>2</sup>
    • An unmatched tag might have the closing tag missing altogether:  500 m<sup>2
    • ... or might be missing the "/" in the closing tag: 500 m<sup>2<sup>
    • Another problem are overlapping tags. E.g., bold italics should be <b><i>like so</i></b>
    • ... and not <i><b>like so</i></b> or <b><i>like so</b></i>
  • If the error already occurs during the preview, it could also be a similar problem in a question stem (yes, even paragraphs need closing tags: <p>This paragraph has one!</p>), or in your exam's prologue or in your epilogue (appendix). You can copy and paste the content of your prologue in this HTML checker (choose "Validate by Direct Input" and choose "Validate HTML fragment" under "More Options").
  • Trying to squeeze too many questions on a page can lead to pagination issues when Dividni chooses mostly longer multi-line options / statements for some script versions. This can lead to page overruns, causing these versions to have a different number of pages from others, which is a no-no. Dividni detects any such page count mismatch automatically and stops production.
  • If you are using parameterised questions, bugs in your C# code can cause a compile errors or runtime error during preview and / or exam production. Ideally, an error message will tell you what is going wrong, however bug hunting may be better performed in the command line version.
  • Printers not obeying PDF page dimensions. If the OMR sheet takes up the entire page so that the fat black markers look rectangular rather than square (and the L-shaped one doesn't look as if made up of three smaller squares), chances are your printer is shaving off the outside of the markers. This is not a common problem but will leave the test / exam unscannable. BASIC RULE: The corner markers and round row and column markers must ALL be visible and undamaged.  
  • PDF readers / printers / virus scanners inserting artifacts such as barcodes, messages, labels, streaks etc. on the OMR sheet. BASIC RULE: The corner markers and round row and column markers must ALL be visible and undamaged.
